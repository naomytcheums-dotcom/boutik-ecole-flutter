# H7 — Scénarios de validation en conditions connectées

Établi le 20 novembre 2026 pour le lot PROD de H7. **Aucun des parcours ci-dessous n'a été exécuté en conditions connectées** : ce document est une procédure prête à jouer, plus la cartographie de ce que les tests **locaux** couvrent déjà.
Les tests locaux ne sont pas rejoués par ce lot (la suite complète est lancée par le chef de projet) : la colonne « test local » indique ce qui **existe** dans le dépôt (fichier et nom lus dans les sources), pas un résultat d'exécution.
Aucun accès à la production, aucune lecture de mot de passe ni de secret pour l'écrire.

## 1. Préconditions communes

1. Les migrations en attente sont appliquées et vérifiées selon `H7_PLAN_PRODUCTION.md` (sans elles, les fonctions `my_department`, `admin_team_member_set`, `company_set_type`, `seller_capable`… n'existent pas et l'application affiche « fonction pas encore activée »). La version web servie est celle du commit déployé (SHA-256 de `main.dart.js` vérifié).
2. Aucun paiement réel : tout montant est un montant de test, sans ordre de paiement Tara Money / MoMo / Orange Money / Notch Pay (voir §4). Aucun SMS ni appel externe réel.
3. Noter pour chaque étape : date, compte utilisé, résultat observé (conforme / non conforme / bloqué), capture. Le registre du §11 sert de feuille de résultats ; ne jamais y inscrire un mot de passe, un code ou une clé.
4. Plusieurs sessions en parallèle : un navigateur (ou profil) par compte, pour ne pas mélanger les rôles. Un téléphone réel est nécessaire pour les étapes marquées « appareil ».
5. Vérifications de base de données (SELECT) : à faire par le propriétaire, en lecture seule, comme dans `H7_PLAN_PRODUCTION.md` ; l'agent de ce lot n'y accède pas.
6. En connexion, **aucune donnée fictive** ne doit apparaître (noms, montants, graphiques, compteurs, avis, notifications) : un état vide explicite, un zéro réel affiché « 0 » et une erreur de chargement affichée comme erreur (jamais « 0 ») sont les seuls comportements corrects. Chaque parcours a une étape « maquette interdite » (test local : `test/journey/maquette_interdite_test.dart`, `h6_admin_propre_test.dart`, `h7_clients_etudiants_propre_test.dart`, `h7_org_dept_direction_propre_test.dart`).

Légende des tests locaux : **Dart** = `test/…/<nom>_test.dart` (`flutter test`) ; **SQL** = `supabase/tests/marketplace_pglite/<nom>.mjs` (PGlite : rejoue toutes les migrations sur une base vide) ; **E2E** = `e2e/tests/<nom>.spec.ts` (Playwright sur base isolée, hors production) ; **Deno** = `supabase/functions/…_test.ts`. Un test SQL prouve la règle serveur sur des données de test, pas sur la production. « non couvert » = aucun test local ne vérifie cette étape.

## 2. Comptes de test : ce qui existe, comment les obtenir, ce qui manque

### 2.1 Existant dans le dépôt (aucun mot de passe n'y figure)

- **Edge Function `admin-test-accounts`** (`supabase/functions/admin-test-accounts/index.ts`) : l'administrateur (profil `admin`, non suspendu) peut (a) créer les comptes manquants (`ensure`), (b) changer le mot de passe de tous les comptes de test (`password`), (c) obtenir un **lien à usage unique** pour ouvrir un compte de test (`login`) ; chaque ouverture est journalisée (`test_login_log`). Seuls les comptes marqués `is_test` sont ouvrables.
  Les comptes créés (un par profil, e-mail `test-<rôle>@boutik-ecole.test`) : **visitor, client, student** (texte de département « Génie informatique »), **company** (« Test Organisation »), **other** (« Test Organisation (ancien rôle fusionné) »), **dept** (« Test Responsable de département », texte « Génie informatique »), **direction, finance, support, admin**. Tests : Deno `admin_test_accounts_test.ts` (« un compte de test par profil, courriels distincts et reconnaissables », « mot de passe : 10 caractères, une lettre et un chiffre »).
- **Écran « Comptes de test »** (`lib/figma/live/test_accounts.dart`, fonctions serveur `test_accounts_list`) : création (« Créer les comptes de test »), changement de mot de passe, ouverture d'un compte par lien, bandeau « Revenir à mon compte » (session de l'administrateur gardée en mémoire seulement). Tests : Dart `test/purchase/comptes_test_test.dart` (« mot de passe des comptes de test : 10 caractères, une lettre, un chiffre », « libellés : un par profil de test », « aucun compte de test : message et bouton de création », « comptes de test : profil, courriel, dernier accès et ouverture ») ; SQL `comptes_test.mjs` (« liste : reservee a l administrateur », « un compte ne se declare pas test lui-meme », « liste : seulement les comptes marques test », « journal : aucun acces direct »).
- **Comment obtenir l'accès** : le **mot de passe est choisi et saisi par l'administrateur** (10 caractères minimum, une lettre, un chiffre) dans l'écran ci-dessus ; il n'est ni renvoyé, ni affiché, ni journalisé, et n'est écrit nulle part dans le dépôt. Sans le saisir, l'ouverture d'un compte de test passe par le lien à usage unique. Aucune clé de service n'est nécessaire côté testeur.
- **Documents** : `docs/final-audit/REPRISE.md` §3 et `INTERVENTIONS_PROPRIETAIRE.md` §2 (nettoyage des comptes de test par `supabase/maintenance/cleanup_test_accounts.sql`, avec garde-fous et ROLLBACK) ; `docs/audit-boutik-ecole/08_TESTS_ET_RESULTATS.md`. Aucun fichier de ce dépôt ne publie d'identifiants.
- **Graine locale** : `tool/audit/replica_seed.sql` ne contient que du catalogue de plateforme (annonces sans vendeur, bornes, paramètres d'établissement), **pas de comptes**. Les scénarios SQL créent leurs propres comptes de fixture (identifiants de la forme `00000000-0000-0000-0000-…`), seulement dans PGlite.
- **Playwright** (`e2e/`) : lit son environnement dans `BASE_URL`, `BE_URL`, `BE_KEY`, `BE_DB`, `STATE` (noms seulement) ; vise une base isolée, jamais la production.

### 2.2 Ce qui manque pour dérouler les six parcours en conditions réelles

| Manque | Conséquence | Comment le combler |
|---|---|---|
| **Rattachement du compte `dept` de test** : la fonction ne renseigne qu'un texte de département ; depuis K3 un compte Département sans `department_accounts` valide ne voit **aucune donnée** | Le parcours Département reste sur l'écran d'attente | L'administrateur rattache le compte à un département **vérifié** (`admin_dept_assign`, aal2 si 2FA) |
| **Permissions des comptes `finance` / `support`** : inscrits sans aucune permission (droits minimaux, K1-3) | Tableaux d'équipe vides, aucun outil | L'administrateur attribue explicitement les permissions voulues (`admin_team_member_set`) |
| **Aucun compte « Sécurité » ni « Technique »** : ces équipes n'ont pas de rôle propre ; un agent est un compte de rôle finance ou support rattaché à l'équipe `security` ou `tech` | Impossible de tester un agent Sécurité / Technique avec les comptes actuels sans réaffecter `support` / `finance` | Attribuer à `test-support` / `test-finance` des permissions `security.*` / `tech.*` (équipes multiples possibles) ; pour plusieurs agents simultanés il faut d'autres comptes de rôle finance/support, non créables par la fonction (un seul par rôle) |
| **Un seul compte par rôle** | Pas de second département (refus inter-départements), pas de seconde organisation (organisation « rivale »), pas de second client (acheteur ≠ vendeur… le client existe mais un seul), pas de second étudiant (éligible vs non éligible), pas de membres d'équipe d'organisation (lecteur, finance, administrateur d'équipe), pas d'agent suspendu | Créer ces comptes par inscription réelle (e-mails dédiés) puis `admin_set_account` ; ils **ne seront pas marqués test** (le marquage n'est posé que par la fonction) et devront être nettoyés à la main : à décider par le propriétaire, ou jouer ces étapes sur une base isolée |
| **Huit organisations** (une par type) : un seul compte `company` de test ; changer le type d'une fiche approuvée la renvoie en vérification | Les 8 types ne se couvrent pas en une passe avec un seul compte | Jouer les types en brouillon l'un après l'autre sur le compte de test (changement de type possible hors vérification), et créer de vrais comptes pour les parcours complets d'approbation |
| **Compte de test `other`** : la fonction crée toujours un profil de rôle `other` par insertion (le déclencheur de fusion ne s'applique qu'aux mises à jour) | Après la migration H1-4, ce compte reste « other » (traité comme `company` par le SQL, mais non fusionné) ; ne pas le prendre comme preuve de la fusion | Preuve de la fusion : les profils `other` **existants** (requête de contrôle du plan) ; correction de la fonction = lot de code |
| **Compte `visitor`** : un visiteur n'a pas de session | Le parcours Visiteur se joue **sans connexion** ; le compte `visitor` ne sert qu'à vérifier le profil `visitor` éventuel | Navigateur sans session |
| **Département et établissement vérifiés, étudiants vérifiés, annonces, commandes réels** : l'état de la production est inconnu de ce lot ; la liste officielle des établissements (MINESUP) n'est pas importée | Les parcours Département, Direction, Étudiant→Vendeur ont besoin de données référentielles réelles | Vérifier en lecture seule ce qui existe ; créer (via l'application) ce qui manque ; sinon base isolée |
| **Authentificateur TOTP** pour les comptes administrateur / agents | Les étapes 2FA (aal2) exigent un facteur vérifié sur un appareil | Application d'authentification du propriétaire (appareil) |
